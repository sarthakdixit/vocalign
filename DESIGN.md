# clone-voice — Design Document

Status: draft v1 · Last updated: 2026-10-05

## 1. Overview

A cross-platform, GPU-accelerated desktop tool for personal voice cloning:

1. User creates a **project**, uploading a reference audio clip (any length) and its reference text.
2. The app preprocesses the audio and **fine-tunes a voice model** on it — training effort scales with how much usable audio is provided (adaptive hybrid: near-instant for a short clip, deeper fine-tune for more data).
3. User enters arbitrary **target text**; the app synthesizes it in the cloned voice.
4. A **dashboard** lists all projects so the user can revisit, retrain, or generate from any of them later.

Top priority, in order: **voice similarity and naturalness** first, everything else (speed, polish) second.

## 2. Goals / Non-goals

**Goals (v1)**
- Cross-platform: developed on Windows, run/tested on Linux (GPU), should also run on macOS.
- GPU-accelerated via CUDA when available, CPU fallback otherwise.
- Local web-style GUI, usable as a quasi-native app window.
- English only.
- Multiple saved projects, each independently trainable and re-usable.
- Personal/local use — no licensing pressure, but we still default to permissively-licensed components.

**Non-goals (v1 — explicitly deferred)**
- Multilingual / cross-lingual cloning.
- Real-time/streaming synthesis (batch generation is fine).
- Multi-user / cloud / hosted deployment.
- Mobile.
- Signed, installer-style packaging (run from source for v1; see Batch 7).

## 3. Key architecture decisions

Grounded in a literature review conducted 2026-10-05 — see [RESEARCH.md](RESEARCH.md) for the full evidence and citations behind anything marked "research-backed" below.

| Decision | Choice | Why |
|---|---|---|
| Training depth | **Adaptive hybrid, GPT stage only** (revised 2026-10-06) | Tiers govern how many epochs the GPT/text-to-semantic stage trains for, scaling with reference-audio duration. The SoVITS/acoustic stage is **not** trained locally at any tier, by confirmed decision below — it stays at its pretrained checkpoint with zero-shot reference conditioning at inference time. |
| Core TTS/voice-clone model | **GPT-SoVITS**, checkpoint **TBD between v2ProPlus and v4** | MIT-licensed, actively maintained (RVC-Boss/GPT-SoVITS, 59k+ stars), purpose-built for exactly this workflow. v2ProPlus was the initial pick on quality-per-compute grounds, but research surfaced a real tension: v2Pro's vocoder is still HiFi-GAN-family, while v3/v4 moved to BigVGAN-family specifically for better robustness on noisy/out-of-distribution audio — which matters more for us than compute efficiency, since we can't assume studio-quality uploads. Now purely a quality/robustness question (see training-scope decision below for why VRAM no longer factors into it). |
| Integration shape | **Confirmed 2026-10-06** (direct inspection of the RVC-Boss/GPT-SoVITS repo, commit `48b1a01`): **subprocess for training**, **direct Python import for inference**. Training (`s1_train.py`, `s2_train.py`/`s2_train_v3_lora.py`) is standalone-script-only — GPT-SoVITS's own `webui.py` drives it via `subprocess.Popen(..., shell=True)`, so our adapter does the same rather than trying to import unstable internals. Inference has a genuinely clean, maintainer-used class API: `GPT_SoVITS.TTS_infer_pack.TTS.TTS` + `TTS_Config` (their own `api_v2.py` imports it directly) — our Batch 4 inference adapter should import this directly instead of shelling out. | Resolves the integration-shape open risk from §13 without guessing. |
| Training scope | **Decided 2026-10-06, confirmed with real training attempts, not estimates: fine-tune the GPT stage locally; the SoVITS stage stays at its pretrained checkpoint, zero-shot, always.** The SoVITS stage (where voice *identity* is actually modeled) does not fit this hardware's VRAM even at the smallest tier — tried gradient checkpointing, CUDA allocator tuning, and a halved `segment_size`; all landed at the same ~3.57-3.58GB-of-3.68GB ceiling, pointing at a fixed baseline cost (both networks + Adam optimizer state under DDP) rather than anything tunable without patching GPT-SoVITS's own training code. The GPT stage reliably completes (3 real runs). `core/train/gpt_sovits_adapter.py`'s `run_sovits_stage`/`build_s2_config` are kept, fully tested up to that hardware wall, as the starting point for a possible future cloud-burst training feature — not called by the local pipeline. Batch 4's inference adapter must point `pretrained_s1` at our fine-tuned checkpoint and `pretrained_s2_g`/`pretrained_s2_d` at the base/pretrained ones. | See §13 for the full attempt-by-attempt log. |
| Fine-tuning method (SoVITS stage, deferred) | Full fine-tune is the only option for v2/v2Pro/v2ProPlus; LoRA exists only for v3/v4's SoVITS/s2 stage (confirmed in `s2_train_v3_lora.py` via the `peft` library, rank 16/32/64/128, default 32). Moot for the local pipeline now (see training-scope row), relevant again only if cloud-burst SoVITS training gets built. | RESEARCH.md Finding 3's "default to PEFT" plan was general TTS literature, not this specific codebase. |
| Forced alignment / ASR | **faster-whisper**, rescoped to **transcript verification + long-clip segmentation** | Originally framed as "alignment for the model." Research shows modern TTS architectures (including GPT-SoVITS's own lineage) don't consume external alignment/duration conditioning at all — Whisper's real job is confirming the user's reference text matches what's actually said, and chopping long uploads into clean segments (RESEARCH.md Finding 1). |
| Candidate ranking / quality scoring | **Whisper WER hard gate, then SECS + UTMOS weighted ranking** | Replaces a vague "Resemblyzer similarity" plan with a two-stage approach validated against human judgment in the literature (RESEARCH.md Finding 4): discard candidates with broken transcription first, then rank survivors by speaker-similarity (weighted higher) and automatic naturalness (weighted lower). |
| GPU scope | **CUDA + CPU fallback only** | Covers the realistic use case; AMD/ROCm and MPS explicitly out of scope to keep the matrix small. |
| GUI | **Gradio UI**, launched either inside a **pywebview** window or as a plain served page | Minimal UI code, cross-platform "for free". pywebview needs a display; GPU boxes are frequently headless, so the launcher supports a `--headless` mode that just serves Gradio on the network. |
| License posture | Personal use, but default to permissive components anyway (MIT/Apache) | No current pressure, but keeps the option to share later cheap. |
| Watermarking | **Deferred**, explicit trigger: revisit if the tool is ever shared/distributed | AudioSeal is cheap and effective but solves a platform-scale detection problem we don't have yet (RESEARCH.md Finding 7). Free interim step: tag AI-generated output in export file metadata (§8.3). |

## 4. Tech stack

| Layer | Choice | Notes |
|---|---|---|
| Language | **Python 3.10** | Confirmed, not a placeholder: current PyTorch (2.14+) happily supports 3.10-3.14, so it isn't the constraint — GPT-SoVITS is. Its own tested range is 3.9-3.11 and its official conda setup uses `python=3.10` directly; 3.9 is already past CPython's security-support end-of-life. `scripts/setup_env.*` warns (doesn't hard-block) if the detected interpreter is outside 3.10/3.11. |
| ML runtime | PyTorch + torchaudio | CUDA build primary; CPU-only build as fallback. Exact CUDA toolkit version depends on the Linux box's driver — discovered in Batch 0. |
| Voice model | GPT-SoVITS (vendored, subprocess/CLI-wrapped — see §9 risk notes) | Training + inference engine. |
| ASR/transcript verification | faster-whisper | Confirms user-supplied reference text matches what's actually said, and segments long uploads — not model-level alignment (see §3). Also the WER hard-gate at generation time. |
| Audio I/O/DSP | ffmpeg (system dep), soundfile, pydub or librosa | Format conversion, resampling. |
| VAD | silero-vad (or webrtcvad as a lighter fallback) | Silence trimming / segment boundaries; also used to compute the speech-to-total-duration ratio (§8.1 threshold). |

| Speaker similarity (SECS) | Resemblyzer, or speechbrain ECAPA-TDNN/WavLM-SV if Resemblyzer proves too coarse | Cosine similarity vs. the centroid of reference embeddings; weighted higher in candidate ranking. |
| Naturalness scoring (UTMOS) | A UTMOS/UTMOSv2 checkpoint | No-reference automatic MOS prediction; weighted lower in candidate ranking, never used as a training objective. |
| Parameter-efficient fine-tuning | `peft` (HF) if GPT-SoVITS doesn't expose LoRA/adapters natively | Only needed if Batch 3 finds GPT-SoVITS's training scripts support full fine-tune only — see §13. |
| GUI | Gradio + pywebview | See §8. |
| Packaging (v1) | Plain `requirements-base.txt` + `requirements-{cuda,cpu}.txt` + setup scripts + `pyproject.toml` (editable install) | Split so torch's CUDA/CPU-specific `--index-url` never shares a file with plain-PyPI packages, avoiding index-precedence ambiguity. Installer/PyInstaller packaging deferred to Batch 7. |
| Testing | pytest, pytest-mock, pytest-cov | Markers `slow` / `gpu` separate heavy/real-model tests from the fast default suite. |

## 7. Project state machine

```
created -> preprocessing -> preprocessed -> training -> trained
                 |                              |
                 v                              v
               error <--------------------------+
```

- `trained` projects can re-enter `training` (retrain with more/different audio) and can **generate** at any time while in `trained`.
- `error` stores a human-readable message and the state it failed from, surfaced in the GUI.

## 8. Core pipelines

### 8.1 Preprocessing
1. Transcode arbitrary input audio (wav/mp3/flac/m4a/...) to mono WAV at the model's expected sample rate via ffmpeg.
2. Loudness-normalize to ≈ -23 LUFS (EBU R128 / ITU-R BS.1770) with a true-peak ceiling.
3. VAD-based silence trimming (leading/trailing + long internal pauses); compute the speech-to-total-duration ratio.
4. Quality gate, surfaced to the user rather than silently accepted (research-backed thresholds, RESEARCH.md Finding 6): hard-block below ~3s usable speech, warn below ~6–10s or below ~60% speech ratio.
5. Optional light denoise — only if noise is detected above a threshold, flagged to the user, never default-on. Research confirms aggressive/default denoising trades noise for lost speaker-identity cues and should stay conservative (RESEARCH.md Finding 6).
6. Transcript verification (not forced alignment — see §3): run faster-whisper over the audio and compare its output to the user-supplied reference text; flag low-confidence or mismatched regions instead of silently training on them.
7. Segment into ~2–10s training chunks on sentence/silence boundaries (from Whisper's own segmentation, not frame-level forced alignment); persist chunk audio + text + confidence to `processed/`.

### 8.2 Training (adaptive hybrid, GPT stage only)

Revised 2026-10-06: tiers below govern the **GPT/text-to-semantic stage only** — real attempts confirmed the SoVITS/acoustic stage doesn't fit this hardware regardless of tier (see §3 "Training scope", §13), so it's always left at its pretrained checkpoint rather than tiered. If cloud-burst SoVITS training gets built later, it will likely need its own, separate tier logic (cloud compute isn't VRAM-constrained the same way, so the right boundaries there probably look different).

1. Sum usable segment duration from `processed/`.
2. Pick a recipe tier from duration — research-backed, not placeholder (RESEARCH.md Finding 2; distinguishes *amount of data used to update weights* from *zero-shot reference-clip length*, which are different axes):
   - `< 15s` → zero-shot only, no weight updates (GPT stage un-tuned too at this tier).
   - `15s–1min` → minimal: 4 GPT-stage epochs.
   - `1–5min` → light: 8 GPT-stage epochs.
   - `5–20min` → standard: 15 GPT-stage epochs.
   - `20min+` → extended: 25 GPT-stage epochs, with a held-out validation slice once that's built.
   (Epoch counts are placeholders pending real quality data, not just timing — see §13.)
3. Device selection: CUDA if available, else CPU — CPU training is likely only practical at the smallest tiers; the UI warns accordingly.
4. Runs as a background process; streams step/epoch/loss/ETA back to the GUI; supports cancel (keep-partial vs. discard, user's choice).
5. On completion: persist the fine-tuned GPT checkpoint + training metadata, transition project to `trained`, then immediately run the quality-signal check (§8.3 step 8) so the user gets a similarity/naturalness read without needing to generate anything manually first. The quality signal necessarily reflects a fine-tuned GPT stage + a zero-shot (pretrained) SoVITS stage together, since that's the real inference-time pairing (§3 Training scope).

### 8.3 Inference / generation

Implemented in Batch 4 (`core/infer/*`), confirmed 2026-10-06 against the real `TTS_infer_pack.TTS`/`TTS_Config` classes (commit `48b1a01`) rather than guessed, the same way Batch 3's training integration was. Confirmed: `TTS_Config` validates the GPT (`t2s_weights_path`) and SoVITS (`vits_weights_path`) checkpoints completely independently with no cross-check - supplying our fine-tuned GPT checkpoint alongside the original pretrained SoVITS checkpoint (§3 Training scope) is exactly what this library supports natively, not a workaround. `TTS.run()` is a generator (`next(tts_pipeline.run(inputs))`, matching the real `api_v2.py`'s own usage) and already handles arbitrary-length text internally with no hard max - so step 3 below is **not** a model input-length workaround, it's purely so each sentence gets its own gate-and-rank pass rather than one bad sentence poisoning (or being hidden inside) a whole-text generation.

1. Load the project's trained GPT checkpoint + the base pretrained SoVITS checkpoint (never both fine-tuned - §3) via `tts_adapter.load_tts()`. GPT-SoVITS's own "prompt audio" (`ref_audio_path`/`prompt_text`) must be a clip from **3-10 seconds**, confirmed via a real `OSError` on the first real generation attempt - the user's full reference recording is never valid there directly. `prompt_selection.select_prompt_clip()` picks the longest in-range clip from the project's own preprocessing chunks (`core/audio/chunk.py`) instead, paired with that chunk's own Whisper-transcribed text (not the user's full reference text, which describes the whole recording, not just this one short clip).
2. Normalize target text (numbers via `num2words`, common abbreviations, whitespace).
3. Split into sentence-level chunks (`chunk_text.py`) for independent per-chunk candidate generation/ranking - see confirmation above.
4. Synthesize a small number of candidates per chunk at varied sampling seed.
5. **Hard gate**: transcribe each candidate with Whisper, compute word-level WER against the chunk's own text; reject candidates above 30% WER (catches garbled/dropped/repeated-word failures that similarity scores alone can miss — RESEARCH.md Finding 4). If every candidate for a chunk is rejected, the least-bad one (lowest WER) is used rather than nothing.
6. **Rank** surviving candidates by a weighted score: SECS via Resemblyzer (speaker-similarity vs. the reference-embedding centroid, weighted 0.7) + UTMOS via `utmos-pytorch` (no-reference naturalness, weighted 0.3 - the original `utmos` PyPI package's fairseq dependency is a known problematic install, avoided); auto-pick the best per chunk.
7. Stitch chunks with a linear crossfade at each join (`stitch.py`).
8. Export WAV (+ optional MP3) to `output/` with generation metadata, including the SECS/UTMOS scores achieved (`export.py`). Tag the exported file's own metadata as AI-generated (near-zero cost, the one watermarking-adjacent step done now — see §3).

**Quality signal** (`core/infer/quality_signal.py`; run once right after training, §8.2 step 5, and re-runnable on demand): synthesize 5 fixed held-out test sentences with exactly **one** candidate each (no best-of-N search - the point is measuring the model honestly, not cherry-picking), average their SECS and UTMOS, and show the user a directional band ("strong match" ≥0.75 SECS / "likely good" ≥0.55 / "uncertain" below - placeholder thresholds pending real calibration data, not research-backed) rather than a raw score — averaging tames the utterance-level noise either metric has on its own (RESEARCH.md Finding 4).

## 9. GUI design & launch modes

Pages: **Dashboard** (list/open/rename/delete projects) · **New Project** (upload audio + text, name it; surfaces the §8.1 quality-gate warnings inline) · **Project Detail** (preprocessing report, start/monitor/cancel training, and the post-training quality-signal band from §8.3) · **Generate** (text in, audio out, per-project generation history with each result's SECS/UTMOS scores).

Launch modes (`scripts/run.py`, one cross-platform script rather than per-OS shell wrappers - pywebview/Gradio are both Python-level concerns, nothing shell-specific to split):
- **Windowed** (default): Gradio server + pywebview window wrapping it. Needs a display/windowing system.
- **Headless** (`--headless`): Gradio server bound to `0.0.0.0`, URL printed to console, no pywebview — for a headless GPU box, accessed from a browser on another machine. This is likely the **primary** mode on the Linux test machine unless it has a desktop environment.

**Implemented in Batch 5** (`gui/*`), built tab-by-tab but all four tabs of one `gr.Blocks()` app, not separate batches - a GUI can't usefully be smoke-tested "half-built" the way the backend batches could, matching this batch's own test-focus framing (manual click-through of the real thing, not mocked unit tests of Gradio wiring itself). Module layout:

- `gui/pipeline/new_project.py`, `training.py`, `generation.py` - one plain, Gradio-free function per tab's real work (`create_and_preprocess_project`, `run_training`, `run_generation`), each unit-tested directly with injectable fakes at the same seams the backend modules already exposed (or newly added here: `ffmpeg_run`/`vad_detector`/`whisper_model` on preprocessing; `run_data_prep_fn`/`run_gpt_stage_fn`/`quality_signal_fn` on training; `load_context_fn`/`whisper_model` on generation). `gui/formatting.py` holds pure display-formatting helpers, also directly tested. `gui/app.py` wires Gradio components to these functions and is deliberately **not** unit-tested - there's nothing meaningful to assert about Gradio callback wiring as plain functions; confidence comes from the manual click-through instead.
- **State machine mapping**: New Project's submit handler runs CREATED→PREPROCESSING→PREPROCESSED (or →ERROR) in one call (Batch 1's preprocessing + writing `dataset.list`). Project Detail's "Start Training" runs PREPROCESSED/ERROR→TRAINING→TRAINED (or →ERROR): recipe selection, GPT-SoVITS's own data-prep scripts, the GPT-stage fine-tune, then the post-training quality signal - all one operation, since data prep only exists to feed the training step. A `zero_shot_only`-tier project skips straight to TRAINED with no checkpoint (`project.config["checkpoint_path"] = None`), since there's nothing to fine-tune - Generate falls back to the base pretrained GPT checkpoint in that case.
- **Progress streaming + cancel**: `gui.pipeline.training.TrainingSession` runs the real multi-step training on a background thread (`run_stage`'s subprocess calls are themselves synchronous); a generator-based Gradio click handler polls `.drain_log()` and yields UI updates every 0.5s until `.done`. Cancel is a `threading.Event` checked via `run_stage`'s existing `cancel_check` contract - cooperative, so it only takes effect between subprocess output lines or at a step boundary, not instantly.
- **Project config as extensible metadata**: `project.config` (already a free-form dict, Batch 2) now carries everything the pipeline needs between steps - `reference_text`, `raw_audio_path`, `dataset_list_path`, `total_speech_seconds`, `recipe_tier`, `checkpoint_path`, `gpt_sovits_version`, `quality_band` - via a new `manager.update_config()`. One GPT-SoVITS vendor checkout + version for the whole app (`core.config.VENDOR_DIR`/`GPT_SOVITS_VERSION`, env-var overridable), not per-project - matches how `scripts/vendor_gpt_sovits.*` actually sets it up.
- **Inference caching**: Generate's `load_inference_context()` caches the loaded TTS pipeline + SECS reference embedding per project, since reloading real models every generation call would be wasteful - but evicts (and frees CUDA memory) whenever a *different* project is requested, since this hardware can't hold two projects' models in VRAM at once (§13). Caching logic and real model construction are split into separate functions specifically so the caching behavior is unit-testable with a trivial fake builder.
- **State-machine fix found while building this**: `VALID_TRANSITIONS` (§7) only allowed `ERROR` as a target from `PREPROCESSING`/`TRAINING`, not from `CREATED`/`PREPROCESSED`/`TRAINED` - a real gap, since a failure can happen before an operation's own first transition even lands (e.g. right after project creation). Every state can now reach `ERROR`.
- `capture_pristine_torch_state()` (naturalness.py, §13) is called exactly once, as the first line of `scripts/run.py`'s `main()` - before `gui.app`/anything GPT-SoVITS-related is imported - so both the training quality-signal step and Generate's UTMOS scoring can rely on it being captured already.
- **Known limitations, not yet fixed**: no guard against double-clicking "Start Training" while one is already running (would likely surface as a real CUDA OOM, not silently); cancel granularity is whatever `run_stage` already provides (checked between output lines, not instantly); the Whisper model used for the WER gate isn't cached across generations the way the TTS pipeline is.

## 11. Testing strategy

- Default `pytest` run must stay fast and dependency-light: anything that needs the real GPT-SoVITS/whisper models or a GPU is marked `@pytest.mark.slow` / `@pytest.mark.gpu` and skipped by default.
- Everything ML-heavy is dependency-injected/mocked in the default suite so tests are meaningful even before heavy ML packages are installed.
- Synthetic audio fixtures (sine tones, silence, noise) cover most of `core/audio` without needing a real voice recording.
- Coverage expectation: high on `core/` (pure logic), lighter on `gui/` (thin wiring layer, verified mostly by manual checklist).

## 12. Collaboration / workflow protocol

This is the agreed process for the whole project, not just this doc:

- Claude writes code and setup/download **scripts** only — never installs packages, downloads models, or executes code/tests on the Windows dev machine.
- One batch at a time: implementation + heavy tests + a short "run this, expect that" note.
- You install/run on the Linux GPU machine (or report you're using the headless path) and send back results — console output, errors, pass/fail.
- Claude fixes/iterates on the reported results before the next batch opens.

## 13. Open risks / decisions to confirm once real installs happen

### Critical finding (2026-10-06): training likely doesn't fit on this GPU at all

Direct inspection of the GPT-SoVITS repo plus its own changelogs and community reports: fine-tuning VRAM needs are **v3 full FT 12-14GB, v3/v4 LoRA 8GB (official floor), v2/v2Pro/v2ProPlus full FT ~6GB+ practical floor with no LoRA option at all**. The target machine has **3.7GB total VRAM**. Community "unsupported GPU" lists for this project explicitly name the desktop "RTX 3050 4G" card (which has *more* VRAM than this laptop part) as incompatible for training. `config.py` itself hard-forces CPU-only training below ~3.6GB total VRAM — this card clears that specific numeric gate by a hair, which is not the same as the real 6-14GB requirement being met. There is no dedicated low-VRAM mode in the project; the community's actual answer for underpowered GPUs is cloud/rented GPUs, not a local setting.

Net: **inference-only (no local weight updates, ever) is the realistic path on this hardware** unless real GPU VRAM availability changes (bigger/different GPU, or a cloud-burst training step). This is a decision for you, not something to silently route around — see the question below before Batch 3's code is written.

**Update (2026-10-06, real run):** less pessimistic than the secondhand research suggested. A real GPT-stage (s1) fine-tune on the `minimal` tier (16 chunks, 50.9s, 4 epochs, fp16) actually ran on the 3.7GB card — model loaded, GPU engaged, epoch 1 completed with reasonable metrics. One transient CUDA OOM warning appeared mid-epoch, but PyTorch recovered from it on its own rather than crashing. So the smallest tier may be genuinely viable locally; deeper tiers (more data, more epochs, and the SoVITS/s2 stage, a different and likely heavier model) remain the open question — the community VRAM figures may still bind there. Treat this as "edge of feasibility for the smallest tier," not "confirmed infeasible everywhere."
- **Real-run fix (2026-10-06):** GPT-SoVITS's checkpoints aren't compatible with PyTorch 2.6+'s `weights_only=True` default on `torch.load` (confirmed: real `UnpicklingError` on `pathlib.PosixPath`, not allowlisted) - an upstream/torch-version skew issue, not ours. `pytorch_lightning` auto-resumes from any checkpoint already sitting in its output dir, which is exactly what triggered the broken load path on a second run. Fix: `run_gpt_stage` now clears that output dir before every run rather than allowing a resume - matches our own semantics better anyway (a training run should reflect current data/settings, not silently continue stale state). Same class of issue likely applies to the SoVITS/s2 stage once we reach it for real; not pre-emptively fixed since its checkpoint-directory convention isn't confirmed yet.
- **Milestone (2026-10-06):** the GPT stage of a `minimal`-tier fine-tune (16 chunks, 50.9s, 4 epochs, fp16) **completed in full** on the 3.7GB card - `top_3_acc_epoch: 0.998`, no crash, no fatal OOM (same transient warning as before, recovered fine). This is the concrete, no-longer-theoretical answer to whether local training can work at all: at the smallest tier, at least the GPT stage genuinely can.
- **Conclusive finding (2026-10-06):** the SoVITS/s2 stage does **not** fit, confirmed with a real crash, not a theoretical one. Checkpoints loaded correctly (confirming `default_paths()` is fully correct for v2Pro), training genuinely started, got 5 iterations into epoch 1, then hit a hard `torch.OutOfMemoryError` during the discriminator's optimizer step - PyTorch reported 3.57 of 3.68 GiB already in use at that point. Matches the earlier secondhand community research (~6GB+ practical floor for v2-family full fine-tune) almost exactly. Two concrete mitigations suggested directly by the real error output (`train.grad_ckpt=True`, `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`) were tried for real - both confirmed active (config/error-message both changed accordingly), neither closed the gap: still crashes at the identical line (discriminator's Adam step) with essentially identical numbers (3.57 of 3.68 GiB in use). That's a razor-thin margin (failing on a 10-20MiB allocation), not an order-of-magnitude gap, so one more targeted lever is in progress: `train.segment_size` (samples/step for the SoVITS decoder, proportional to per-step memory; exposed as `FineTuneJob.segment_size`, explicit opt-in rather than a silent default since unlike grad_ckpt it has a real quality/stability tradeoff) via `scripts/smoke_test_batch3.py --segment-size <value>`. First real attempt used 8192 and got *past the OOM entirely* - genuine progress - but crashed with a shape-mismatch `RuntimeError` instead: `segment_size` must be an exact multiple of the model's `hop_length` (640; confirmed via the real tensor-size numbers in the error), which 8192 isn't but the original default 20480 and the next candidate 10240 both are. `build_s2_config` now validates this itself (raises with a suggested valid value) so this specific mistake can't happen silently again. If 10240 still doesn't get a full epoch through, that's the point to treat local SoVITS training as conclusively infeasible on this card and revisit the original three-way fork (build-and-test-for-real / inference-only / cloud-burst training) with a real, fully-tried answer in hand - the SoVITS stage is where voice *identity* is actually modeled, so "GPT stage works, SoVITS doesn't" is not yet a usable voice-cloning pipeline on its own.
- **Real-run fix (2026-10-06):** the "clear stale checkpoint dir before a fresh run" fix (above) hit its own bug: `shutil.rmtree` raised `OSError: Directory not empty` on a real run, immediately after confirming it had removed everything - a transient sync-lag symptom on some filesystems (the project path is under `/media/...`, Linux's conventional mount point for external/removable drives, which is a plausible cause and worth keeping in mind for other filesystem-heavy steps too, e.g. Batch 6's larger downloads). `_clear_dir()` now retries briefly (3 attempts, short delay) before giving up, rather than failing outright on what's very likely a non-real conflict.
- **Conclusive (2026-10-06):** halving `segment_size` (20480 -> 10240) only bought one extra iteration (7 vs 5-6) before an essentially identical OOM ceiling (~3.57-3.58 GiB of 3.68 GiB used, same as every other attempt). If the bottleneck were per-step activation memory, that lever should have mattered far more than it did. The much more likely explanation: the baseline cost of both networks (generator + discriminator) plus their Adam optimizer states, under `torch.multiprocessing.spawn` even for one GPU, already consumes nearly the whole card before any step's activations are counted. None of the remaining config knobs touch that - closing this gap would mean patching GPT-SoVITS's own training code (removing DDP for the single-GPU case, offloading optimizer state), a materially different and larger kind of change than anything tried so far. **This is the stopping point for config-level tuning.** Confirmed with real data, not estimates: the GPT stage reliably works on this hardware (3 successful runs); the SoVITS stage - where voice identity is actually modeled - does not, and further tuning isn't likely to change that. Revisit the three-way fork from before Batch 3 with this in hand.
- **Real-run fix (2026-10-06):** `build_s2_config` was missing `train.gpu_numbers`, which `s2_train.py` reads at module import time with no fallback - this was already in the confirmed webui.py override list from earlier research (§3/Finding above); it just didn't make it into the actual function. Fixed directly (`"0"` for single-GPU) rather than re-researching something already confirmed.
- **Real-run fix (2026-10-06):** the PYTHONPATH gap found for the 4 prep scripts also applies to the training scripts - `s2_train.py` imports `tools.my_utils` (`tools/` lives at the repo root, outside what Python's default script-directory `sys.path[0]` covers), and `run_gpt_stage`/`run_sovits_stage` weren't setting `PYTHONPATH` at all (only `data_prep.py` was). `s1_train.py` happened not to need it, which is why this wasn't caught earlier. Extracted into one shared `gpt_sovits_adapter.build_env()` that both the training-stage calls and `data_prep.py` now use, instead of two copies of the same logic.

- **GPT-SoVITS integration shape — confirmed, no longer open.** Subprocess for training (matches what `webui.py` itself does), direct Python import (`TTS_infer_pack.TTS`) for inference. See §3.
- **Does GPT-SoVITS expose LoRA/adapter/PEFT tuning natively — confirmed, no longer open.** Only for v3/v4's SoVITS stage, never for the GPT stage, never for v2-family. See §3. This resolves the question but doesn't change the VRAM finding above — LoRA's 8GB floor is still ~2x this GPU's budget.
- **v2ProPlus vs v3 vs v4 checkpoint choice** — now secondary to the VRAM finding. If the path forward is inference-only, this becomes a pure quality/robustness question again (noise-robustness still favors v3/v4's BigVGAN-family vocoder, per RESEARCH.md Finding 5) with no training-VRAM downside to weigh against it, since nothing trains locally either way.
- **Vendoring GPT-SoVITS itself**: `scripts/vendor_gpt_sovits.{sh,ps1}` clone the repo pinned to commit `48b1a0169a28582a8984402f82cf438d3bfa6aca` (the commit our adapter's script names/args were confirmed against) and run GPT-SoVITS's own installer (`install.sh --device CU126 --source HF`), which downloads ~5.2GB of pretrained checkpoints and installs GPT-SoVITS's own Python deps (pytorch_lightning, peft, funasr, etc.) into whatever environment is active. This is a slice of what was planned for Batch 6, pulled forward out of necessity - nothing can really train without it. Real pretrained-checkpoint paths per version (confirmed against `config.py`'s own lookup dicts) are encoded in `core/train/gpt_sovits_adapter.py`'s `default_paths()`. **Open risk**: running GPT-SoVITS's installer in the same env as our own torch 2.14.1+cu126 could touch/conflict with it - not yet observed for real, flagged to watch for when the vendoring script is actually run.
- **GPT-SoVITS's own data-prep pipeline** (`GPT_SoVITS/prepare_datasets/1-get-text.py` → `2-get-hubert-wav32k.py` → `2-get-sv.py` [v2Pro/v2ProPlus only] → `3-get-semantic.py`) must run before either training stage - confirmed and implemented in `core/train/data_prep.py`, env-var interface verified directly against `webui.py`'s caller code rather than guessed. None of the 4 scripts hard-require a GPU (all fall back to CPU automatically, just slower) - meaning data prep itself may succeed on this hardware even where the actual fine-tune stage runs out of VRAM, which is useful diagnostic signal either way.
- **Real-run fix (2026-10-06):** all 4 prep scripts need `PYTHONPATH` set to include both the vendored repo root and `GPT_SoVITS/` itself - `1-get-text.py` does no `sys.path` setup of its own at all, and `webui.py`'s own `Popen` call doesn't set this either (empirically verified with a disposable probe script against the real repo, not guessed). `data_prep.py`'s `_build_prep_env` handles this now.
- **Real-run fix (2026-10-06):** `build_s1_config`/`build_s2_config` now load GPT-SoVITS's own real template config (`s1longer.yaml`/`s1longer-v2.yaml`, `s2.json`/`s2v2Pro.json`/`s2v2ProPlus.json` - confirmed verbatim against the repo, v1/v2/v3/v4 all share plain `s2.json`) and overlay only the keys `webui.py` itself overlays, instead of building a config from scratch. The from-scratch version was missing real acoustic hyperparameters (`filter_length` etc.) and crashed `3-get-semantic.py` with `AttributeError: 'HParams' object has no attribute 'filter_length'` on the first real run. Also confirmed: `3-get-semantic.py` specifically gets the **unmodified template path**, not a mutated temp config - `data_prep.py`'s `run_get_semantic` now points there directly via `gpt_sovits_adapter.s2_template_path()`.
- **Real-run fix (2026-10-06, Batch 4):** `tts_adapter.load_tts()`'s `from GPT_SoVITS...` import is a direct in-process import (unlike training's subprocess calls), so `build_env()`'s `PYTHONPATH`-based fix doesn't reach it - confirmed with a real `ModuleNotFoundError` on the first real smoke test run, since setting `PYTHONPATH` on an already-running process has no effect on that process's own `sys.path`. Fixed with a new `gpt_sovits_adapter.ensure_on_sys_path()` (same two entries as `build_env()`, applied to `sys.path` instead), called by `scripts/smoke_test_batch4.py` right before `load_tts()`.
- **Real-run fix (2026-10-06, Batch 4):** that fix wasn't enough on its own - a second real run got two import-layers deeper into `TTS_infer_pack` and hit `ModuleNotFoundError: No module named 'ERes2NetV2'`. Root cause confirmed directly against the real repo at the pinned commit: `GPT_SoVITS/sv.py` does `sys.path.append(f"{os.getcwd()}/GPT_SoVITS/eres2net")` - a CWD-relative hack, not a proper import - which only resolves because GPT-SoVITS's own `api_v2.py` is meant to be launched with CWD already at the repo root (confirmed `api_v2.py` itself adds nothing beyond what `ensure_on_sys_path()` already replicates; it leans on `sv.py` entirely for the `eres2net` case). A direct in-process import doesn't get that CWD for free the way a subprocess's `cwd=` argument does. Fixed with a new `gpt_sovits_adapter.chdir_to_repo_root()` context manager (temporarily `os.chdir`s into the vendored repo root, restores the original CWD in a `finally`), wrapping `scripts/smoke_test_batch4.py`'s `load_tts()` call. Chosen over manually replicating every such hidden subdirectory one `ModuleNotFoundError` at a time, since matching upstream's real CWD assumption covers whatever else in this import chain might rely on it the same way, known or not yet discovered. Caveat for Batch 5: `os.chdir` is process-wide, not thread-local - fine for a single-request script, but worth revisiting if the GUI backend ever serves concurrent generation requests.
- **Real-run fix (2026-10-06, Batch 4):** past the GPT-SoVITS import/CWD issues above, loading actually succeeded for real - fine-tuned GPT + base pretrained SoVITS + BERT + CNHuBERT all loaded together, VITS weights reported "All keys matched successfully," confirming the mixed-checkpoint approach works exactly as the research predicted. The next real failure was unrelated to GPT-SoVITS entirely: `resemblyzer` (for SECS) pulls in `webrtcvad`, which does `import pkg_resources` - deprecated in setuptools 67.5.0, fully removed in 82.0.0, and the environment had 84.0.0. Not a code bug, a stale transitive dependency vs. a too-new setuptools; fixed by pinning `setuptools<82` in `requirements-base.txt` (still satisfies torch's own `>=77.0.3`).
- **Real finding (2026-10-06, Batch 4):** past every import/environment issue above, the TTS pipeline loaded and generation actually started - then hit a real, substantive constraint rather than a bug: GPT-SoVITS's `TTS_infer_pack.TTS._set_prompt_semantic` hard-rejects any `ref_audio_path` outside **3-10 seconds** (`OSError: Reference audio is outside the 3-10 second range`). The full-length reference recording (any length, per the original requirements) is therefore never valid as `ref_audio_path` directly - something §8.3's pipeline description hadn't accounted for. Fixed with a new `core/infer/prompt_selection.py`: reads Batch 3's already-written `dataset.list` (one line per preprocessing chunk, `audio_path|speaker|language|text`), measures each clip's real duration, and picks the longest one within 3-10s, paired with *that chunk's own* Whisper text (not the user's full reference text - pairing the right short clip with the wrong, whole-recording text would have been a second, separate correctness bug). `scripts/smoke_test_batch4.py` no longer takes a `reference_text` argument - it derives the prompt pairing from Batch 3's output instead, and only still uses the raw `audio_path` argument for the SECS reference embedding (Resemblyzer handles arbitrary-length audio natively, so the full clip is fine, arguably better, there). Longest-in-range is a reasonable default, not a research-backed optimum - worth revisiting against real output quality once more projects exist to compare.
- **Real-run fix (2026-10-06, Batch 4):** past the 3-10s prompt-clip fix, a real generation actually ran end to end - both candidates synthesized, both re-transcribed by Whisper for the WER gate - and only failed on SECS scoring: `librosa.util.exceptions.ParameterError: Audio data must be floating-point`. Root cause confirmed as much as the real repo's own code allows (its `api_v2.py` packs the raw `run()` output through `sf.write()` or, for AAC, pipes it to ffmpeg as raw `s16le` - both point to integer PCM, not float): `TTS.run()` yields raw int16 audio, which is fine for `sf.write()` (dtype-tolerant) but not for Resemblyzer's SECS scoring, which requires already-float samples when given an array directly rather than loaded from a file. Fixed in `tts_adapter.synthesize()`, which now normalizes to float32 right at the source (scaled by the dtype's own range, not a hardcoded 32768, so it's correct for any integer PCM width, and a no-op if ever already float) - so every downstream consumer (ranking/SECS/UTMOS, stitching, export) uniformly gets what the rest of this codebase already assumes everywhere else.
- **Real-run fix (2026-10-06, Batch 4):** past the SECS dtype fix, the pipeline got all the way to UTMOS scoring and hit `AttributeError: module 'utmos_pytorch' has no attribute 'Scorer'` - the one function in this module that had been explicitly flagged as unconfirmed the way the GPT-SoVITS integration was, and the guess was wrong on two counts, not one. Confirmed against the real package README: the class is `UTMOSScoreTorch(device=...)`, and its `.score()` takes an already-mono-16kHz torch tensor directly, not a numpy array plus a separate sample_rate. Fixed in `naturalness.py`: `predict_mos()` now takes an injectable `preprocess_fn` (same pattern as `similarity.py`'s `compute_embedding`) that converts+resamples to the required tensor shape by default, and unwraps the real `.score()` call's tensor-shaped result via `.item()` rather than assuming a plain float. Scorer runs on CPU deliberately, not CUDA - it's a reporting metric, not on the critical path for voice identity, and not worth adding VRAM pressure on an already-tight card mid-generation.
- **Real finding + fix (2026-10-06, Batch 4):** past the UTMOS API fix, scoring reached the real model and then hit `NameError: name '_in_projection' is not defined` **inside the vendored GPT-SoVITS repo's own code** (`GPT_SoVITS/AR/modules/patched_mha_with_cache.py`). Root cause: GPT-SoVITS monkey-patches `torch.nn.functional.multi_head_attention_forward` **globally** (process-wide, not scoped to its own calls) to add KV-caching for its autoregressive GPT-stage decoding - and that patch has its own gap, hit only by utmos-pytorch's unrelated wav2vec2-based model (a different calling pattern than GPT-SoVITS's own narrower internal usage apparently ever exercises). Not fixable by patching our own code alone, since the conflict is a third-party-vs-third-party collision sharing one process-wide namespace. Fixed with `naturalness.capture_pristine_torch_state()` - called once, as early as possible (the first line of `scripts/smoke_test_batch4.py`'s `main()`, before `load_tts()` ever runs) - which saves the real, unpatched function before GPT-SoVITS gets a chance to replace it; `predict_mos()` then temporarily restores it just around the one call that needs it, putting GPT-SoVITS's patched version back immediately after so the *next* TTS synthesis call still gets what it needs. Same category of lesson as the sys.path/CWD findings above: importing a third-party inference library can have global process-wide side effects that only surface once something else in the same process needs the thing it silently changed.
- **Milestone (2026-10-06): the Batch 4 real smoke test completed end to end for the first time.** `scripts/smoke_test_batch4.py` against the Batch 3 checkpoint + base pretrained SoVITS + target text "Hello, name is Sarthak": output `generated_output.wav`, 1.74s, SECS=0.78 (clears `quality_signal.py`'s "strong match" ≥0.75 threshold - one real data point against those placeholder numbers, still not enough to call them calibrated), UTMOS=4.16/5, no WER-gate rejections (`low_confidence=False`), 12.2s wall time. This is the first real confirmation that the whole hybrid architecture - GPT fine-tuned locally, SoVITS zero-shot at its pretrained checkpoint, mixed-checkpoint `TTS_Config` loading, automatic 3-10s prompt-clip selection, SECS+UTMOS ranking - actually produces output, not just that each piece loads. Subjective quality (does it actually sound like the reference speaker) is still pending the user actually listening to the file - the numbers above are directional signals, not a substitute for that.
- **Real-run fix (2026-10-06, Batch 5):** first real launch of `scripts/run.py --headless` hit a real `TypeError: unhashable type: 'dict'` inside Jinja2's template cache, entirely inside gradio/starlette/jinja2's own code (never touching `gui/app.py`) - gradio 4.44.1's Jinja2-based page rendering breaks under starlette >= 1.0, and gradio 4.44.1 itself doesn't pin an upper bound on starlette (confirmed against its real PyPI metadata: only `fastapi<1.0`, no starlette constraint at all), so pip had installed starlette 1.7.0 transitively. First attempt (`pip install --upgrade gradio`, landing on 6.29.1) fixed that but caused a **second**, more serious regression: gradio 6.x's own `gradio-client`/`hf-gradio` sub-packages require `huggingface-hub>=1.16.0`, directly conflicting with `transformers`'s `huggingface-hub<1.0` ceiling (transformers/tokenizers are pulled in transitively by utmos-pytorch's wav2vec2-based model, not a direct dependency here) - a real case of one fix's blast radius touching an already-working, unrelated part of the stack (Whisper/UTMOS). Resolved by reverting to `gradio<5` (keeps huggingface-hub in transformers' required range) plus an explicit `starlette<1.0` pin (fixes the original Jinja2 break directly, rather than relying on gradio's own, absent, upper bound). Both pinned in `requirements-base.txt` now, alongside an explicit `huggingface-hub<1.0,>=0.34.0` floor so a future `pip install --upgrade` of anything else can't drift it out of range again.
- **Real-run fix (2026-10-06, Batch 5):** first real click-through got all the way through a full training run (25 epochs, extended tier, real GPU utilization confirmed via `nvidia-smi` at 84%/3.3GB during a transient OOM-warning scare that turned out to be normal, recoverable load) - then Generate hit a real `CUDA out of memory` trying to allocate 1.63GiB with 2.19GiB "already in use" before that allocation even started. Root cause: the post-training quality-signal step runs *in-process* (unlike training itself, which is a subprocess whose GPU memory is fully released when it exits) and was loading its own independent TTS pipeline - which PyTorch's caching allocator doesn't hand back to the OS just because the Python object went out of scope. Generate then tried to load a *second*, completely separate TTS pipeline on top of that, on a 3.68GB card that can't hold two. Fixed by having the quality-signal step reuse `gui.pipeline.generation.load_inference_context()` - the same cache Generate itself uses - instead of loading its own copy: one model load, shared between "post-training check" and the first real Generate click, which also means that first Generate click is now fast (model's already warm) rather than needing a fresh load. This required reordering `_train()` to persist `checkpoint_path` *before* running the quality signal (the shared loader looks it up from the project's own saved config), and making the quality-signal step non-fatal to the training outcome - it's a diagnostic extra, and failing it (e.g. a future, different OOM) must not undo an already-valid, already-trained checkpoint. Same underlying lesson as Batch 4's monkey-patch finding: a long-running, single-process GUI accumulates state (here, GPU memory) across what look like independent operations in a way a one-shot script never surfaces.
- **Real-run fix (2026-10-06, Batch 5):** the previous fix's "share the cached model" change didn't fully resolve Generate's OOM - a retry with the same 500-word text failed identically. Diagnosed precisely via the progress-log capture added for this: the failure's `progress_log` was *empty*, meaning it died before even the first chunk's synthesis started - ruling out the 500-word text and per-chunk accumulation entirely (a red herring). The real console log confirmed it: the OOM hit immediately after "Loaded the voice encoder model," i.e. inside `compute_embedding()` on the *full raw reference clip*. This project's reference recording was long enough to land in the `extended` recipe tier (20min+ of usable speech), and feeding tens of minutes of raw audio into Resemblyzer in one call - on top of GPT+SoVITS+BERT+HuBERT already occupying nearly the whole 3.68GB card - exceeded the ~130MB left. The earlier design rationale ("more audio = a more stable embedding, let it use the full clip") didn't account for this hardware having near-zero headroom once everything else is loaded. Fixed by capping the audio fed into the SECS reference embedding to 60s (`gui.pipeline.generation._cap_reference_audio()`, a hardware-driven safety cap, not a research-backed optimum) - a speaker embedding doesn't meaningfully improve from tens of minutes of audio, so this costs effectively nothing in quality. Because the quality-signal step was already refactored to share this same code path, the fix applies to both Generate and the post-training quality signal automatically.
- **Real-run fix (2026-10-06, Batch 5):** first real 500-word Generate attempt (after the SECS-embedding OOM above was fixed) produced audio with a real, reported "couple of words, then a gap, then a couple more words" pattern, and the result correctly reported `low confidence - WER gate rejected every candidate for at least one chunk`. The user's actual text included `**global politics**` - literal markdown bold syntax, almost certainly from pasting out of a document/chat that preserved formatting. `core/infer/text_normalize.py`'s `normalize_text()` expanded abbreviations and numbers but did nothing about markdown, so those asterisks reached GPT-SoVITS's text frontend as literal characters absent from both the base checkpoint's and this project's own fine-tuning transcripts - degrading that one chunk's synthesis badly enough to fail the WER gate outright, which is exactly the symptom described. Fixed by adding markdown stripping to `normalize_text()` (bold/italic/strikethrough/inline-code/headings/links unwrapped to their inner text via paired patterns, run before a catch-all for any leftover unpaired symbol) - this resolves the gap/dropout pattern specifically. Separately, the overall "a little robotic" quality impression is not something this fixes - that's the already-understood consequence of SoVITS staying zero-shot regardless of training data (§3 Training scope), same category as Batch 4's "fine, not great but fine" verdict.
- **Confirmed hardware** (2026-10-05, via `check_gpu.py` on the Linux box): NVIDIA GeForce RTX 3050 Laptop GPU, CUDA 12.6, ~3.7GB total VRAM, torch 2.14.1+cu126. VRAM is tight enough that the LoRA/adapter default (§3, RESEARCH.md Finding 3) is likely necessary, not just preferable — worth re-checking against actual memory usage once Batch 3 runs a real fine-tune.
- **Python version**: resolved to 3.10, see Tech Stack table — still worth a glance at `check_gpu.py`/`setup_env.*` output in case your box's default `python3` triggers the version warning.
- **Recipe-tier step counts/timing** — the duration *boundaries* are now research-backed (§8.2), but how many steps/how long each tier actually takes on your specific GPU is still only confirmed once we see real training runs.
- **pywebview system deps on your Linux distro** (GTK/Qt backend) — if missing or the box is headless, `--headless` mode is the real primary path; worth knowing which applies before Batch 5.
- **Citation confidence**: most of RESEARCH.md is peer-reviewed/primary, but the XTTS-v2 duration-ablation thesis and the 2026 RVCBench paper are newer/unreviewed — their specific numbers are directional, not settled; don't hard-code thresholds derived only from those two without a sanity check against real results.
